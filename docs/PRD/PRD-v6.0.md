## 原始需求符合性结论

V5.0 已覆盖 `docs/PRD/EQS.md` 的主要产品概念，但尚不能作为完整、可实施、可验收的需求基线，具体缺口如下：

| 编号 | V5.0缺口 | V6.0处理结果 |
|------|-----------|--------------|
| GAP-01 | 用户端、服务端仅明确微信小程序/H5，未覆盖原始需求中的App | 将iOS/Android App纳入公测交付范围，统一使用Uni-app构建 |
| GAP-02 | 报价、合同、付款节点、资质、打卡、纠纷缺少核心数据模型 | 补充对应数据实体及关键约束 |
| GAP-03 | 核心API未覆盖报价、合同、节点验收、资质核验、打卡、争议处理 | 补充端到端核心API清单 |
| GAP-04 | “平台托管/充值/提现”表述可能被理解为平台自建资金池 | 明确由持牌支付机构或银行提供分账/存管能力，平台只保存业务单据和外部流水号 |
| GAP-05 | “平台仲裁”易与法定仲裁混淆 | 定义为合同约定的专家评审与平台调解，并保留法定仲裁、诉讼权利 |
| GAP-06 | CAD、报告模板、保险品类、3秒推荐等原始要求缺少明确验收口径 | 补充优先级、阶段边界和可测试验收标准 |

**结论**：V6.0 完成上述修订后，原始需求均已被映射为功能、业务规则或阶段性规划；第21章追踪矩阵是范围验收的最终依据。第三方支付、电子签章和政府数据核验的实际上线时间仍受服务商签约及接口授权约束。

## 1. 项目概述

### 1.1 项目背景

工程服务业（设计、造价、地勘、监理）长期存在以下痛点：

| 角色 | 痛点描述 |
|------|----------|
| 甲方/业主 | 找服务方靠关系、比价难、进度不透明、结算纠纷多 |
| 服务方 | 商务成本高、获客难、回款周期长、信用体系缺失 |
| 行业整体 | 信息化程度低、标准化程度差、信任成本高 |

### 1.2 产品定位

**一句话定位**：工程服务业的"美团+滴滴"——一站式智慧交易与协作平台。

**核心价值**：
- 对甲方：像"点外卖"一样找工程服务——简单、透明、可控
- 对服务方：像"滴滴抢单"一样接项目——高效、低成本、有背书

### 1.3 业务闭环

```
+----------------------------------------------------------------------+
|BUSINESS FLOW                                                         |
+----------------------------------------------------------------------+
|Publish Request -> Match/Claim -> Online Contract -> Delivery         |
|-> Result Confirm -> Milestone Settlement -> Credit Accumulation      |
+----------------------------------------------------------------------+
```

> **注解**：发布需求 -> 匹配/抢单 -> 线上签约 -> 过程交付 -> 成果确认 -> 节点结算 -> 信用沉淀

### 1.4 项目范围

| 范围维度 | 说明 |
|----------|------|
| 服务类型 | 造价咨询、工程监理、地质勘察、工程设计 |
| 项目规模 | 初期聚焦 50万以下中小型项目 |
| 地域范围 | 初期以单城市为试点，验证模式后全国推广 |
| 终端覆盖 | 需求方与服务方共用业务客户端：微信小程序为主，H5和iOS/Android App同步覆盖；运营方使用PC管理后台 |

## 2. 业务背景与市场分析

### 2.1 行业现状

中国工程服务业市场规模超万亿，但数字化渗透率不足5%。主要特征：

- **高度分散**：大量中小型事务所、个体工程师
- **关系驱动**：获客主要靠人脉，缺乏公开透明的交易市场
- **交付非标**：服务成果质量难以量化评估
- **结算低效**：付款周期长，纠纷处理机制不完善

### 2.2 竞品分析

| 竞品类型 | 代表产品 | 优势 | 劣势 |
|----------|----------|------|------|
| 综合招标平台 | 公采网、比地招标 | 资源多、流程规范 | 侧重招投标，轻协作 |
| 垂直SaaS | 广联达、鲁班 | 专业工具强 | 偏工具，无交易闭环 |
| 本地服务商 | 各地设计院/造价所 | 本地化服务好 | 信息化程度低、获客难 |

**EQS差异化定位**：不做纯工具，不做纯招标，而是"交易+协作+信用"三位一体。

### 2.3 目标市场

**初期切入市场**（MVP阶段）：
- 监理服务：高频、刚需、标准化程度相对较高
- 工程造价审计：决策快、频次高、成果可标准化

**中期扩展市场**：
- 地质勘察
- 工程设计（方案/施工图）

**远期市场**：
- 全品类工程服务
- 建材/设备租赁交易

## 3. 产品目标与成功指标

### 3.1 产品目标

| 阶段 | 目标 | 时间节点 |
|------|------|----------|
| 冷启动期 | 完成MVP上线，验证业务闭环 | 第1个月 |
| 成长期 | 单城市月活用户突破1000，月交易额突破500万 | 第2个月 |
| 扩张期 | 完善全功能，管理后台上线，覆盖单城市 | 第3个月 |

### 3.2 核心KPI

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 供需匹配率 | 发布需求后24小时内获得报价的比例 | ≥80% |
| 推荐响应时间 | 提交完整项目条件后返回首屏推荐结果的服务端耗时 | P95≤3秒 |
| 交付准时率 | 按约定节点完成交付的比例 | ≥90% |
| 用户满意度 | 服务完成后评分平均值 | ≥4.5/5.0 |
| 纠纷率 | 产生纠纷的订单占比 | ≤2% |
| 复购率 | 同一甲方30天内再次发单的比例 | ≥30% |

## 4. 用户角色与用户画像

### 4.1 用户角色定义

#### 角色一：甲方/需求方

| 子类型 | 典型画像 | 核心需求 |

#### 角色二：服务方/供给方

| 子类型 | 典型画像 | 核心需求 |
|--------|----------|----------|
| 造价事务所 | 3-20人规模，持有一级/二级造价师资质 | 稳定获客、快速回款、品牌曝光 |
| 监理公司 | 10-50人规模，持有监理资质 | 项目资源、人员调度、合规管理 |
| 设计院 | 10-100人规模，持有设计资质 | 拓展业务渠道、项目协作 |
| 地勘院 | 5-30人规模，持有勘察资质 | 设备共享、项目匹配 |
| 独立工程师 | 持有注册证书的个人 | 灵活接单、信用背书 |

#### 角色三：平台运营方

| 子类型 | 职责 |
|--------|------|
| 运营人员 | 审核资质、处理纠纷、客户服务 |
| 技术人员 | 系统维护、功能迭代、数据安全 |
| 财务人员 | 结算管理、对账核验、发票处理 |
| 评审专家 | 接受争议案件指派、披露利益冲突并提交专业评审意见 |

**平台方四大核心职能**：

| 职能 | 说明 |
|------|------|
| 规则制定 | 制定平台交易规则、服务标准、违约与争议处理规则 |
| 资金监管 | 对接持牌机构监管资金，平台按节点验收提交处理指令但不触碰资金 |
| 争议处理 | 组织专家评审和平台调解，并衔接法定仲裁或诉讼 |
| 数据沉淀 | 沉淀交易、信用、行业指数数据，反哺运营决策 |

### 4.2 用户画像

**甲方用户画像 - 张经理**

- 期望：稳定项目来源、快速结算、减少商务成本

## 5. 功能需求详细说明

### 5.1 用户端（微信小程序/H5/App）—— 需求方使用

#### 5.1.1 智能发单模块

**功能描述**：甲方通过标准化表单发布工程服务需求，系统自动识别项目类型并生成服务清单。

**详细功能**：

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 项目类型选择 | 房建、市政、装修、水利等，支持多选 | P0 |
| 项目信息填写 | 项目名称、地址、规模、预算范围、期望工期 | P0 |
| 智能清单生成 | 根据项目类型自动生成服务需求清单 | P0 |
| 附件上传 | 支持上传CAD图纸、PDF文件、图片，单文件最大50MB | P0 |
| 发布范围设置 | 公开发布 / 指定服务商邀请 | P1 |
| 预估报价 | 系统根据项目信息给出参考价格区间 | P1 |
| 模板保存 | 支持保存常用发单模板，下次快速复用 | P2 |

**业务规则**：
- 项目金额≥50万需上传立项批文
- 同一项目最多可邀请5家指定服务商
- 发布后24小时内未响应自动推送提醒

#### 5.1.2 服务超市模块

**功能描述**：按服务类型分类展示入驻服务商，支持多维度筛选和比较。

**详细功能**：

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 分类浏览 | 按造价、监理、地勘、设计四大类展示 | P0 |
| 筛选条件 | 地区、资质等级、评分、价格区间、服务类型 | P0 |
| 服务商主页 | 资质证书、团队规模、过往案例、用户评价、信用分 | P0 |
| 收藏关注 | 收藏服务商，关注其动态 | P1 |
| 智能推荐 | 基于历史发单记录和偏好，推荐匹配度最高的服务商 | P1 |
| 对比功能 | 最多选择3家服务商进行横向对比 | P2 |

#### 5.1.3 进度看板模块

**功能描述**：实时跟踪服务交付进度，类似"物流追踪"体验。

**状态流转**：
```
Published -> Accepted -> Field Work -> Drafting -> Reviewing
-> Delivered -> Accepted by Client -> Settled
```

> **注解**：已发布 -> 已接单 -> 现场作业/勘察中 -> 报告编制中 -> 审核中 -> 已交付 -> 验收完成 -> 已结算。不同服务类型可隐藏不适用节点，但状态转换规则一致。

**详细功能**：

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 进度可视化 | 时间轴展示项目进度 | P0 |
| 节点提醒 | 关键节点（提交初稿、终稿等）自动通知 | P0 |
| 消息中心 | 与服务方的沟通记录、系统通知 | P0 |
| 交付物预览 | 在线预览PDF/图片格式的交付物 | P1 |
| 进度催办 | 对超期项目一键催办 | P1 |

#### 5.1.4 订单支付与节点结算模块

**功能描述**：平台对接持牌支付机构或银行的订单支付、分账/存管能力，按节点验收发起资金释放指令。平台不吸收存款、不形成自有资金池，只保存订单、支付状态及外部流水号。

**详细功能**：

| 功能点 | 说明 | 优先级 |
|--------|------|--------|
| 订单支付 | 支持微信支付、银行转账及对公支付，资金直接进入持牌机构提供的受监管账户 | P0 |
| 节点设置 | 自定义付款节点（如：初稿30%、终稿70%） | P0 |
| 验收确认 | 甲方在线确认交付物，触发资金释放 | P0 |
| 退款流程 | 未完成节点可申请退款，有争议时进入专家评审与平台调解流程 | P1 |
| 结算管理 | 服务方查看待结算、结算中、已到账和失败记录；平台向第三方发起结算指令 | P0 |
| 发票管理 | 服务方开票、甲方收票、平台验真及交易关联，支持纸质发票邮寄状态跟踪 | P1 |
| 账单查询 | 交易明细、支付记录、退款记录和结算记录 | P0 |

**业务规则**：
- 上线前由法务、财务与持牌机构确认采用银行存管、支付机构担保交易或合规分账方案；未完成签约和验收不得上线真实资金交易
- 资金直接进入持牌机构提供的受监管账户，平台不得截留、挪用或以内部余额替代真实资金
- 验收后T+1工作日释放至服务方账户
- 争议订单向持牌机构申请止付或冻结，依据双方协议或生效法律文书处理
- 默认使用“节点验收放款”；“先服务、后付款”仅面向平台审核通过且双方书面约定的企业信用订单，不承诺资金担保

### 5.2 服务端（微信小程序/H5/App）—— 服务方使用

#### 5.2.2 抢单/竞价模块

**功能描述**：服务方对公开项目进行抢单或报价竞争。

**详细功能**：

| 功能点 | 说明 | 优先级 |

| 维度 | 权重 | 计算规则 |
|------|------|----------|
| 交付准时率 | 30% | 按时交付次数 / 总交付次数 |
| 质量评分 | 30% | 甲方验收评分平均值 |

## 9. 微信生态集成

### 9.1 微信小程序登录

**流程**：
```
Open Mini App -> wx.login() Code -> Exchange OpenID -> Issue JWT -> Return
```

> **注解**：用户打开小程序后，前端调用`wx.login()`获取临时`code`，后端换取`openid`并签发JWT后返回客户端。

**接口**：`POST /api/v1/auth/wx-login`

| 参数 | 类型 | 说明 |
|------|------|------|
| code | string | wx.login()获取的code |
| userType | int | 用户类型：1-甲方 2-服务方 |

**返回**：
| 字段 | 类型 | 说明 |
|------|------|------|
| token | string | JWT Token |
| user | object | 用户信息 |
| isNew | boolean | 是否新用户 |

### 9.2 微信支付集成

**流程**：
```
Create Payment -> Licensed Provider -> User Confirmation -> Signed Callback
-> Reconciliation -> Update Payment Status
```

> **注解**：平台服务端通过已签约的微信支付商户能力创建订单；用户确认支付后，系统验签并幂等处理回调，再以第三方对账结果校准状态。是否使用担保交易、分账或银行存管，以法务审查和通道实际签约能力为准。

**接口**：`POST /api/v1/payments`（`channel=wechat`）

| 参数 | 类型 | 说明 |
|------|------|------|
| orderId | int | 订单ID |
| amount | int | 金额（分） |

**支付回调**：`POST /api/v1/payments/notify/wechat`

## 14. 冷启动与运营策略

### 14.1 种子用户策略

- **服务方**：先邀请几家本地的、信誉好的设计院/造价所入驻，提供"免抽佣期"或"流量扶持"
- **需求方**：从开发区、产业园获取小型的工程报建项目，提供“免费发布、持牌机构资金保障”服务

### 14.2 业务闭环验证

- **小型项目切入**：先不做上亿的大项目，而是做"小型工程签证、零星维修预算、临时监理"
- **标准化报告**：平台提供标准的《地勘报告模板》、《造价审核清单》等，降低服务方交付门槛

### 14.3 支付与信任

- 默认采用“节点验收放款”：通过持牌支付机构或银行完成支付、止付、退款和结算，平台不自建资金池
- “先服务，后付款”作为企业信用订单的可选模式，仅在双方书面约定且服务方明确接受风险后启用
- 支付通道、电子签章和资质核验服务未完成合同签署、合规评审及沙箱验收前，只允许使用Mock环境

### 15.1 技术风险

### 15.2 业务风险

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| 服务方资质造假 | 平台信誉受损 | 中 | OCR+人工双重审核，引入第三方数据核验 |

> 【工程快捷服务】平台简介

工程快捷服务，是专为工程服务业打造的"一站式智慧交易与协作平台"。

**平台模式**：连接"设计、造价、地勘、监理"四大核心服务商，为业主提供"发单-匹配-签约-交付-结算"的全流程线上化服务。

| 外部能力 | 必须满足的准入条件 | 未满足时的处理 |
|----------|--------------------|----------------|
| 支付、分账或存管 | 合同与费率确认；法务/财务评审通过；回调验签、幂等、退款、止付和日对账测试通过 | 仅使用Mock或沙箱，不开放真实支付入口 |
| 电子签约 | 服务商资质审查；实名/意愿认证；签署回调、文件哈希和存证验证通过 | 使用线下合同并人工登记，不显示“在线签署成功” |
| 主管数据核验 | 确认数据来源、接口授权、使用目的和留存期限 | 转人工核验并保存依据，不宣称已联网核验 |
| 保险服务 | 与持牌保险机构签约；产品条款、投保人告知和理赔入口完成审核 | 不展示可购买状态，不以平台名义承保 |

### 21.4 核心验收场景

| 验收ID | 场景 | 前置条件 | 预期结果 |
|--------|------|----------|----------|
| AC-01 | 需求方发布标准化需求 | 已登录并选择项目与服务类型 | 系统生成对应服务清单；必填项、附件和金额规则校验通过后发布成功 |
| AC-02 | 服务方报价并由甲方中选 | 服务方资质有效，项目处于报价期 | 可提交金额、周期和方案；服务方只见脱敏排名；甲方中选后只生成一个待签约订单 |
| AC-03 | 生成并签署合同 | 订单、报价、付款节点已确认 | 合同内容与订单一致；双方完成签署后合同归档，订单才可进入待支付状态 |
| AC-04 | 按节点支付、验收和结算 | 通道沙箱可用，合同已签署 | 回调验签且幂等；验收前不可结算；验收后按节点金额结算；账单与通道流水一致 |
| AC-05 | 服务方资质审核 | 已上传营业执照、资质、人员证书和社保材料 | OCR结果须人工确认；证书过期、人员或社保不一致时不得通过；审核全程留痕 |
| AC-06 | 智能匹配 | 存在不同地区、资质与信用分的服务方 | 无匹配资质者被排除；排序可解释；首屏推荐接口P95不超过3秒 |
| AC-07 | 图纸与交付物协作 | 订单进行中且用户有项目权限 | PDF/图片可预览；CAD可上传下载和留版本；批注绑定文件版本；无权限用户不可访问 |
| AC-08 | 多端核心闭环 | 小程序、H5、iOS和Android构建可用 | 四端均可完成登录、发单/报价、消息、交付、验收和账单查询，状态保持一致 |
| AC-09 | 现场打卡 | 监理或地勘订单已配置项目位置 | 仅点击打卡时请求定位；记录距离与时间；拒绝定位可走照片人工审核；不后台持续定位 |
| AC-10 | 信用评分更新 | 已完成订单、评价或争议结案 | 分项数据可追溯；按既定权重重算；同一事件重复通知不得重复计分 |
| AC-11 | 争议处理 | 订单有未结算节点且一方发起争议 | 立即申请止付；双方可举证质证；专家执行回避；结果与处理依据留痕；页面明示法定救济权利 |
| AC-12 | 标准模板交付 | 运营方已发布有效模板 | 服务方可下载签约时版本；缺少必交材料时无法提交；模板升级不改变既有订单版本 |

### 21.5 版本完成定义

V6.0作为开发基线必须同时满足以下条件：

- 追踪矩阵中对应版本的P0需求均有测试用例，且不存在未说明的需求缺口。
- Go与JavaScript/TypeScript单元测试覆盖率均不低于80%，核心业务闭环具备集成测试，关键用户路径具备E2E测试。
- 支付、签约、资质、定位和争议处理通过安全与隐私评审，审计日志能够还原关键状态变更。
- 外部能力不满足第21.3节准入门槛时必须降级或关闭，不能用模拟成功结果进入生产环境。
- 产品、研发、测试、运营、财务和法务共同确认范围及遗留风险后，版本方可发布。

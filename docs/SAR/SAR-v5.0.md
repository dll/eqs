## 0. 执行摘要

### 0.1 总体结论

**当前项目适合演示和开发验证，不具备生产发布条件。**

项目已经形成 Go/Gin 后端、Vue 管理后台、Uni-app 客户端和 MySQL/SQLite 数据模型的完整工程骨架，当前实际注册 91 条 API、AutoMigrate 25 个模型；基础构建、单元测试和 3 条 H5 E2E 可以运行。服务商、消息通知、文件下载、进度看板、AI 分析和日志等后续功能也已经补入代码。

但“已有路由”和“生产闭环”之间仍有明显差距。身份体系允许客户端自选管理员角色，固定验证码在所有环境直接通过，支付及电子签回调没有验签，多类订单、合同、结算、资质、争议和文件资源缺少对象级授权。结合管理员可自注册和演示数据清库接口，存在直接接管后台与清空业务数据的路径。支付、签约、OCR、文件存储等仍是 Mock 或元数据占位，客户端交付、支付、争议入口仍有 Toast 占位，核心交易链路不能按 PRD 验收。

因此，SAR-v4.0 的“达到生产可用状态”和安全五星结论不成立；V5.0 将其纠正为“生产阻断”。

### 0.2 核心判断

| 维度 | 审核结论 | 主要依据 |
|------|----------|----------|
| 需求完整性 | 部分实现 | 多数模块有表或接口，但 AC-01~12 均存在闭环、外部服务或验收证据缺口 |
| 后端实现 | 可开发验证 | 91 条路由、25 个模型；对象级授权、状态机和事务完整性不足 |
| 客户端实现 | 部分可用 | 基础页面可运行；交付、支付、争议等关键动作仍为占位 |
| 管理后台 | 基础运营可用 | 页面和路由守卫存在；业务权限仍依赖不可信 JWT 角色，部分列表无分页 |
| 安全与合规 | 生产阻断 | 管理员自注册、固定验证码、回调无验签、批量越权、默认密钥、敏感数据明文 |

## 1. 审核口径

### 1.1 状态定义

| 状态 | 定义 |
|------|------|
| 已实现 | 代码、界面、权限、状态流转和必要测试均能支持需求验收 |
| 部分实现 | 存在模型、接口或页面，但业务闭环、权限、外部服务或验收证据不完整 |
| 未实现 | 无可用代码，或仅有数据表、文案、Toast、Mock 返回值 |
| 生产阻断 | 功能看似存在，但安全、资金、合规或数据完整性风险禁止生产使用 |
| 未验证 | 代码或配置存在，但本次没有环境或证据证明指标成立 |

### 1.2 证据优先级

1. 本次在当前工作区执行的测试、构建和审计结果；
2. 当前代码、工作流和部署配置；
3. PRD 与历史 SAR 的声明；
4. 无法从仓库或本次实测复核的生产运行描述，仅作为背景，不作为通过证据。

### 1.3 审核限制

- 未连接腾讯云生产数据库、Redis、CVM、Caddy 或第三方服务；生产域名与服务状态未复测。
- 未执行真实支付、退款、分账、电子签、短信、OCR、COS、主管部门核验。
- 未执行渗透测试、SAST、DAST、密钥扫描、许可证合规扫描。
- 未执行 k6 压测、4G 首屏测试、数据库慢查询基准和长时间稳定性测试。
- 未执行备份恢复、RTO/RPO、故障切换和部署回滚演练。
- `govulncheck` 与 `golangci-lint` 未安装，本次不能给出对应扫描结论。

## 4. 实现审核

### 4.1 后端与 API

#### 已形成的能力

- Gin 路由、GORM 模型、MySQL/SQLite 双驱动和 Redis 初始化结构完整；
- 91 条路由覆盖用户、项目、报价、订单、合同、支付、争议、资质、文件、消息、配置和后台运营；
- 参数化 GORM 查询降低了常规 SQL 注入风险；
- 部分高风险动作已有基础状态检查，例如节点未验收不能结算、争议存在时拒绝结算；
- 文件下载接口比列表和批注接口更完整，已经校验上传者、项目甲方、订单服务方和管理员；
- Admin 路由统一应用认证和 `RequireAdmin`，前端也有路由守卫。

#### 主要实现问题

| 问题 | 证据 | 影响 |
|------|------|------|
| 对象授权未统一 | 多个 handler 直接按路径 ID `First`/`Where`，未校验当前用户与资源关系 | 批量 IDOR，难以逐接口保证安全 |
| 状态机分散 | handler 内直接更新数字或字符串状态，无统一状态迁移器 | 可跳状态、规则漂移、并发冲突 |
| 事务边界不足 | 支付回调、签约、结算、争议结案包含多次独立更新 | 中途失败会产生跨表不一致 |
| 错误处理不完整 | 多处 `Update`、`Create`、审计写入错误被忽略 | API 返回成功但数据未完成 |
| 响应模型直接复用数据库模型 | Project 预加载完整 User，User JSON 包含 phone/wx_open_id | 可能过度暴露个人信息 |
| 列表分页不一致 | 项目、服务商、用户、订单、流水等列表直接全量查询 | 数据增长后响应和内存不可控 |
| N+1 查询 | 进度看板逐项目查订单、逐订单查节点 | 项目数增长后数据库压力显著 |
| 双重 schema 路径 | AutoMigrate 与单个 `001_init.sql` 并存 | 缺版本化迁移、回滚和生产变更审计 |

### 4.2 数据模型与数据治理

25 个模型数量与 PRD 一致，但“有字段”不等于满足数据要求：

- `attendance_records.longitude/latitude` 为 float64 明文；
- `supplier_qualifications.certificate_no` 为明文；
- User 的手机号、微信 OpenID/UnionID 无字段级加密或脱敏层；
- 项目地址和经纬度可通过项目响应返回，缺少用途和角色控制；
- 文件表只保存客户端提交的 `storage_key`、URL 和哈希元数据，未证明对象真实存在；
- 审计日志为普通业务表，无 WORM、防篡改、签名链、归档和 180 天保留策略；
- 无数据分类分级、删除/匿名化、用户授权记录、访问导出和隐私请求流程；
- 无生产迁移版本表、回滚脚本、数据字典一致性检查和种子数据隔离策略。

### 5.4 合规判断

- 支付：当前只能作为 Mock 演示，不得接收真实资金或宣称存管、分账、退款、止付能力。
- 电子签：当前不满足可靠电子签名的身份、意愿、完整性和存证要求，只能走线下合同登记降级方案。
- 个人信息：定位、手机号、OpenID、证书信息等缺少最小化、单独授权、加密、留存和删除机制，不能认定满足个人信息保护要求。

- AI：向外部模型发送项目数据前，应建立数据分类、脱敏、用户告知、供应商协议、内容审计和人工复核。

| Admin 大 chunk | ECharts、Element Plus 和页面包 | 路由懒加载、manualChunks、按图表加载、分析重复依赖 |
| 内存监控无上限/重启丢失 | `monitor.go` 进程内统计 | Prometheus/OpenTelemetry 指标、直方图和外部时序存储 |
| 缺缓存策略 | 服务商、公开配置、版本、主题等 | 明确缓存键、TTL、失效和一致性，不把 Redis 当正确性前提 |
| 文件链路缺失 | 仅元数据登记 | 客户端直传 COS + 服务端回调校验，避免 API 承担大文件流量 |

### 7.2 架构问题

- Handler 同时承担鉴权、业务规则、状态迁移、持久化和外部服务调用，难以复用和测试；
- 全局 `model.DB`/`model.RDB` 增加并发测试和依赖替换难度；
- 支付、电子签仅有名义 Provider，实际代码仍直接实例化 Mock；
- 状态字段混用数字和字符串，缺少数据库约束及统一枚举；
- API 没有 OpenAPI 契约、生成客户端和兼容性检查，PRD 路由数已明显漂移；
- 错误码、分页、幂等键、审计上下文和追踪 ID 未形成统一规范。

### 7.3 建议目标架构

1. 引入 `Service + Repository + Policy` 的薄层次，只为支付、合同、订单、争议等复杂域落地，不进行全仓形式化重构；
2. 将对象授权集中为可组合 Scope，例如“订单参与方”“项目所有者”“平台财务”“指派专家”；
3. 将支付和签约抽象为真实接口，Mock 只能由测试依赖注入，生产配置禁止构造 Mock；
4. 对关键状态变更使用数据库事务、幂等键、乐观锁或条件更新，并用 Outbox 发送通知；
5. 以 OpenAPI 生成接口清单和前端类型，使 PRD、路由、测试和文档能自动比对。

## 8. CI/CD、部署与运维

### 8.1 CI 审核

当前 CI 会构建后端、Admin、H5/小程序/App 资源，并运行后端、Client、Admin 测试。主要缺口：

- CI 不运行 Client E2E；
- 不生成或门禁覆盖率；
- 不运行 `govulncheck`、依赖漏洞门禁、SAST、密钥扫描和镜像扫描；
- Client 构建产物未归档 H5，命名和发布物校验不完整；
- lint 允许大量 warning，未形成逐步收紧基线；
- 无 MySQL/Redis 服务容器集成测试；
- 无迁移前后兼容和 OpenAPI 破坏性变更检查。

### 8.2 CD 审核

`cd.yml` 在每次 push 到 main 时独立触发，不依赖 `ci.yml` 成功。由此可能在测试失败时仍部署。其他问题包括：

- 后端停止后直接覆盖二进制，无蓝绿/滚动、原子切换和自动回滚；
- 只检查 systemd active，不检查真实健康接口和核心依赖；
- Admin/H5 直接覆盖目标目录，可能产生新旧静态资源混合；
- 后端、Admin、H5 三个部署 job 独立，失败时可能形成跨端版本不一致；
- 没有部署锁、环境审批、变更记录、数据库迁移阶段和回滚演练；
- Release 为 draft，且当前 HEAD 没有匹配版本 Tag，发布身份不可直接追溯。

### 8.3 部署配置风险

| 等级 | 配置问题 | 影响 |
|------|----------|------|
| P1 | systemd 使用 `User=root` | 后端被利用后获得主机最高权限 |
| P1 | systemd 写 `Environment=DB_PASSWORD=${DB_PASSWORD}` | systemd 不按 shell 展开，可能注入字面值或造成部署漂移 |
| P1 | Compose 暴露 MySQL 3306、Redis 6379 | 扩大攻击面；Redis 无密码 |
| P1 | nginx `/health` 指向未注册的 `/api/v1/health` | 健康检查不可用 |
| P1 | nginx 未配置 `client_max_body_size 50m` | 与 PRD 上传规格冲突 |
| P2 | nginx 缺代理超时、限流、gzip、静态缓存和安全头 | 性能、稳定性和安全基线不足 |
| P2 | Dockerfile 最终进程位于 `/root` 且未切非 root 用户 | 容器最小权限不足 |
| P2 | Dockerfile 暴露 8080，CVM systemd 使用 8090 | 多套配置存在端口漂移 |
| P2 | Gin 未配置可信代理 | 客户端 IP、审计和限流依据不可靠 |

注：审核期间工作区的 `eqs-cvm.conf` 出现未提交的 SPA fallback 调整，该修改改善 Admin history 路由回退，但不改变上述健康检查、上传大小、代理和安全头结论。

### 8.4 可观测性与恢复

- 当前监控为进程内计数，重启即丢失，不能支撑 99.9% SLO；
- 无 Prometheus/OpenTelemetry、结构化请求 ID、分布式追踪和集中日志；
- 无 P0 告警规则、通知渠道、值班表、Runbook 和事件复盘模板；
- 无 MySQL 自动备份、binlog、异地保存、加密、校验和恢复演练；
- Redis 的定位未明确，若承载验证码和限流，应定义不可用时的安全降级；
- 无容量水位、慢查询、第三方错误率、支付对账差异和审计写失败告警。

## 10. 优化与增强路线图

### 10.1 第一阶段：安全止血（1~2 周）

目标：关闭所有可直接接管、伪造资金状态或破坏数据的路径。

1. 固定公共注册角色，拆分管理员/专家创建流程，登录后从数据库读取角色和状态；
2. 固定验证码仅存在于显式测试构建，增加 SMS 频控、一次性、失败锁定和风控；
3. 为订单、项目、合同、节点、资质、争议、文件、打卡、消息和评价建立统一授权策略；
4. 暂时从所有可共享环境下线路由级支付/签约回调和 Demo clean，直至正式安全能力完成；
5. 生产模式拒绝默认密钥启动，收紧 CORS、可信代理、错误响应和安全头；
6. 增加 P0 的自动化攻击回归用例。

阶段出口：P0=0，越权测试和回调伪造测试全绿，安全负责人签字。

### 10.2 第二阶段：核心业务闭环（3~6 周）

目标：完成可验收的“发单→报价→中选→签约→支付→执行→交付→验收→结算→评价/争议”。

1. 补智能发单规则、服务清单、附件、批文、预估价和邀请关系；
2. 实现交付模板、真实文件链路、预览、版本和清单阻断；
3. 接入持牌支付及合规电子签，完成沙箱与异常联调；
4. 补齐 Client 支付、交付、争议、聊天和文件工作台；
5. 修正信用五维模型、争议责任方和重算幂等；
6. 完成争议的三专家、回避、质证、复核和执行；
7. 编写跨角色、跨端、跨状态的核心 E2E。

阶段出口：AC-01~12 逐条有自动化或签字验收证据，Mock 不进入真实业务配置。

### 10.3 第三阶段：质量与发布工程（2~4 周，可并行）

1. 去除入口 BOM，建立全仓覆盖率报告与 80% 门禁；
2. 页面、权限、回调、事务、MySQL/Redis 集成测试进入 CI；
3. 修复高危依赖，加入 Node/Go/SAST/secret/container 扫描；
4. CD 改为 CI 成功后手动审批或受保护环境触发；
5. 建立原子静态资源目录、健康检查、回滚、迁移和版本一致性校验；
6. 建立备份、binlog、恢复演练、监控告警和 Runbook。

阶段出口：发布清单全绿，回滚和恢复演练通过，当前提交有唯一版本 Tag 和制品摘要。

### 10.4 第四阶段：性能与产品增强（持续）

1. 先统一分页并消除看板 N+1，再执行 1000 并发和 P95 基准；
2. 优化 Admin 分包、H5 首屏、静态缓存和图片资源；
3. 推荐系统增加地区、资质范围、服务类型、价格、履约和评价特征，并提供解释；
4. 服务超市增加案例、评价、收藏、对比和多维筛选；
5. AI 建立离线评测集、幻觉/敏感信息检测、模型降级和成本指标；
6. 在核心交易稳定后，再立项会员、保险、打印邮寄和行业数据服务。

## 11. 生产发布门槛

满足以下全部条件前，不得将当前版本标记为“生产可用”：

- P0 问题全部关闭，P1 无未接受的高风险项；
- 真实支付、电子签、文件和资质核验按准入条件通过沙箱及生产前联调；
- AC-01~12、NFR-AC-01~06 和 DEP-01~05 有可复核验收记录；
- 后端、Client、Admin 有效覆盖率均不低于 80%，核心权限与交易 E2E 全绿；
- 生产依赖无未处置高危漏洞，Go/Node/镜像/密钥扫描进入 CI；
- CD 只部署通过 CI 的不可变制品，支持健康检查、原子切换和自动回滚；
- 备份恢复演练达到 RTO/RPO，监控告警和 P0 响应流程可用；
- 1000 并发、API P95、推荐 P95、首屏和上传指标经同一版本实测通过；
- 敏感数据加密、脱敏、授权、留存、删除和审计满足上线地区合规评审；
- 当前提交、四处版本、Tag、Release 和制品哈希一致。

### 11.1 可接受的当前用途

| 环境 | 是否建议 | 约束 |
|------|----------|------|
| 本地开发 | 可以 | 使用隔离 SQLite/测试数据，不接入真实支付和个人信息 |
| 内部演示 | 有条件可以 | 网络隔离、演示账号、Mock 标识醒目、禁用外部回调和清库风险 |
| 外部试用 | 暂不建议 | P0 未关闭，存在账号接管和越权风险 |
| 生产环境 | 禁止 | 不满足安全、资金、合规、质量和运维门槛 |

## 12. 最终结论

EQS 已经从“需求和页面原型”发展为可以构建、运行和演示的多端工程，91 条 API、25 个数据模型、基础管理后台和客户端页面为后续迭代提供了可用基础。PRD V8.0 所列 provider、消息和文件下载缺口已有代码进展，SAR-v4.0 记录的部分增强也确实存在。

但是，本次全面审核发现历史报告把“接口已注册”“Mock 可返回成功”“前端路由守卫存在”误判为“需求验收”和“生产安全”。当前最重要的工作不是继续增加页面或商业增强，而是先关闭身份、回调、对象授权、Demo 清库和默认密钥等 P0，再完成真实资金、签约、文件、交付和争议闭环，并用有效覆盖率、权限负向测试、核心 E2E、压测和恢复演练建立发布证据。

**V5.0 审核结论：开发/演示级，可继续迭代；生产发布不通过。**
